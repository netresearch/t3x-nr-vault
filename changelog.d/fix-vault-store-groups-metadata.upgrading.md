- `vault:store` now refuses invocations it used to accept: `--metadata frontendAccessible=…` (set it in the backend module or through `VaultService`), `--metadata groups=…` (use `--groups`), `--metadata metadata=…`, `--metadata source|table|field|flexField|uid=…`, a non-numeric `--metadata expiresAt|owner|scopePid=…`, a pair without `=`, and a `--groups` value that is not a positive group UID (`--groups="1,2"` used to become group 0). Options are checked before the secret value is read.
- `vault:store --groups` on an existing secret that holds a value now changes its groups, which needs `secret.manage_policy`. The default `cliAllowedOperations` does not include it, so such a call by the plain CLI user is denied; add `secret.manage_policy` to the allowlist or use `--as-provisioner` with a user that holds it. `--metadata` on an existing secret now reads its metadata first to merge, which needs read access to the secret; the read and the store are two steps, so a metadata write by another process between them can be lost (#524).
