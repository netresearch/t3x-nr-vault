- Secrets created through a TCA or FlexForm vault field, a record copy, `vault:migrate-field` or the migration module now store their record link under `metadata`, where the orphan cleanup reads it. Before, the callers passed the link as top-level `store()` options, which the service ignores, so the cleanup never saw these secrets (#565). The migration module writes the same keys as the other callers (`source`, `table`, `field`, `uid`) instead of `originalTable`, `originalColumn` and `originalUid`.
- Both orphan cleanups (scheduler task and `vault:cleanup-orphans`) share one check: a linked secret is deleted once its retention period has passed and its linked record (table, uid) no longer exists, deleted rows counting as existing. Inside a workspace the vault field hooks and both migrations link the live record, not the workspace version, so publishing does not orphan the secret. `vault:cleanup-orphans` now keeps a secret whose table or connection it cannot resolve, as the scheduler task already did, and looks the table up on its own connection; both cleanups accept the same sources: `tca_field`, `flexform_field`, `record_copy`, `flexform_record_copy` and `migration`.
- The parameters of `vault:migrate-field` and `IdentifierValidator::looksLikeVaultIdentifier()` that carry a plaintext value are `SensitiveParameter`s, so a stack trace rendered with `zend.exception_ignore_args` off does not show it. The verify page of the migration module highlights failed and erroneous rows again; the row class was printed as Fluid text.
