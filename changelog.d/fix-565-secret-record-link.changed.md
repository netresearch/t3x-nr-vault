- `vault:migrate-field` now replaces the field value with the vault identifier, as its documentation describes; before, it left the plaintext in the field and the new secret unreferenced. This is the new default and needs no option: code that read the plaintext from the migrated column must resolve the identifier through the vault (`VaultFieldResolver::resolveFields()`).
- `VaultAdapterInterface::getMetadata()` now includes disabled secrets, like `retrieveIncludingDisabled()`: `LocalEncryptionAdapter` (and through it the HashiCorp and AWS adapters) used to return null for a disabled secret, although `updateMetadata()` merged into it. A custom adapter should do the same.
- `vault:cleanup-orphans` exits 1, and the orphan cleanup scheduler task reports a failed run, whenever a secret was kept because its check failed on a query or connection error, on every path (nothing to delete, `--dry-run`, cancelled, deleted). A secret whose link names no field, an unknown table or an unknown field is kept and listed with a warning as before and does not fail the run; delete it by hand or restore the table or field. `OrphanReferenceCheckerInterface::getUnresolvedReferences()` entries carry a `transient` flag that tells the two apart.
