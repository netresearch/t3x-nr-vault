- Secrets created through a TCA or FlexForm vault field, a record copy, `vault:migrate-field` or the migration module now store their record link under `metadata`, where the orphan cleanup reads it. Before, the callers passed the link as top-level `store()` options, which the service ignores, so the cleanup never saw these secrets (#565). The migration module writes the same keys as the other callers (`source`, `table`, `field`, `uid`) instead of `originalTable`, `originalColumn` and `originalUid`.
- The orphan cleanup (scheduler task and `vault:cleanup-orphans`) deletes a linked secret once its retention period has passed and no row of the linked table, deleted rows included, holds the identifier in the linked field. Secrets of published workspace versions, translations sharing a field and copies are kept; the secret of a discarded workspace version is removed. Inside a workspace the vault field hooks link the live record, not the workspace version. Columns named by a reserved word are recognised. `vault:cleanup-orphans` keeps a secret whose table, connection or column it cannot resolve, as the scheduler task already did, and lists such secrets after the check. After the confirmation it checks each secret again right before deleting it, and reports a secret whose re-check failed as not checked, with the reason, exiting non-zero. Both cleanups accept the same sources, including `flexform_record_copy`.
- The orphan cleanup never deletes a secret younger than 15 minutes, even with 0 retention days: record copies store a secret a moment before they write its identifier into the record. It checks the linked row by primary key first. That read is a fast path for "held" only: when the linked row does not hold the identifier, the database itself is asked, so its collation (case, trailing spaces under MySQL's defaults) decides as it does for every lookup that resolves the secret.
- `vault:migrate-field` and the migration module protect the plaintext while they move it. They refuse a column that cannot hold the identifier, read the field back after the update (a CHAR column's padding is not a mismatch), and store the record link only once the row holds the identifier, so orphan cleanup cannot delete a secret kept after a failed write. They delete the secret just stored only when the row still or again holds the plaintext: the update matched no row, or the original value was written back and read back; otherwise they keep the secret and name it. An update that changes more than one row fails the record. Both UPDATEs name the value the row is expected to hold, so a value an editor saved after the migration read the row is never overwritten, and a mismatching read-back is restored only when it is a truncation of the identifier. The value is stored first (a Create entry); the record link is added afterwards with its own MetadataUpdate entry. With the local adapter both steps are transactions of their own; with the HashiCorp and AWS adapters, which have none, a failure of the link's read-back or audit write takes the link back with a targeted metadata write. Adding the link reads only the registry row, never the remote backend, so an outage of HashiCorp Vault or AWS Secrets Manager does not leave the row unlinked. When taking the link back fails too, the row is reported with its link state unknown and a critical log entry. The link needs `secret.create` (as the creation did), not `secret.rotate`, reaches disabled secrets too, and counts as written only when a read-back shows it. A row whose link could not be added is reported as migrated without its link; the run exits non-zero and the module shows the column as Partial. The migrations' store is create-only, so two concurrent runs generating the same identifier cannot overwrite each other, and a secret is deleted again only while it is the one this run stored. A disabled secret counts as holding its identifier: it is neither overwritten nor wrapped. Both migrate hidden and time-restricted records but not deleted ones; the deleted check follows TCA `ctrl.delete`, and a table without TCA is filtered on its `deleted` column. Tables mapped to another database connection are looked up there.
- `vault:migrate-field` refuses a `--uid-field` that does not exist or whose value several rows share, no longer wraps a UUID v7 value that is the identifier of an existing secret in a new secret (also with `--force`; a plaintext equal to a secret's friendly name is still migrated, and the skipped line does not print the value), fails a record whose identifier check against the vault errors and continues with the next one, reports a non-numeric `--uid-field` value as it is instead of as 0, and recognises a field named by a reserved word. The migration module no longer overwrites an existing secret whose identifier its pattern produces, and lists the reasons of failed rows on the verify page; a column with only row failures stays Partial.
- The orphan cleanup scheduler task logs through the logger it receives as a LoggerAware task when the scheduler builds it without dependency injection (TYPO3 13.4 unserializes tasks and sets it in `__wakeup()`; 14.3 falls back to `makeInstance()`, which sets it). Before, such a task logged nothing.
