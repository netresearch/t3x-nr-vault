- Secrets created through a TCA or FlexForm vault field, a record copy, `vault:migrate-field` or the migration module now store their record link under `metadata`, where the orphan cleanup reads it. Before, the callers passed the link as top-level `store()` options, which the service ignores, so the cleanup never saw these secrets (#565). The migration module writes the same keys as the other callers (`source`, `table`, `field`, `uid`) instead of `originalTable`, `originalColumn` and `originalUid`.
- The orphan cleanup (scheduler task and `vault:cleanup-orphans`) deletes a linked secret once its retention period has passed and no row of the linked table, deleted rows included, holds the identifier in the linked field. Secrets of published workspace versions, translations sharing a field and copies are kept; the secret of a discarded workspace version is removed. Inside a workspace the vault field hooks link the live record, not the workspace version. Columns named by a reserved word are recognised. `vault:cleanup-orphans` keeps a secret whose table, connection or column it cannot resolve, as the scheduler task already did, and lists such secrets after the check. Both cleanups accept the same sources, including `flexform_record_copy`.
- The orphan cleanup never deletes a secret younger than 15 minutes, even with 0 retention days: record copies store a secret a moment before they write its identifier into the record. It checks the linked row by primary key first. That read is a fast path for "held" only: when the linked row does not hold the identifier, the database itself is asked, so its collation (case, trailing spaces under MySQL's defaults) decides as it does for every lookup that resolves the secret.
- `vault:migrate-field` and the migration module protect the plaintext while they move it. They refuse a column that cannot hold the identifier, read the field back after the update (a CHAR column's padding is not a mismatch), and store the record link only once the row holds the identifier, so orphan cleanup cannot delete a secret kept after a failed write. They delete the secret just stored only when the row still or again holds the plaintext: the update matched no row, or the original value was written back and read back; otherwise they keep the secret and name it. An update that changes more than one row fails the record. Both UPDATEs name the value the row is expected to hold, so a value an editor saved after the migration read the row is never overwritten, and a mismatching read-back is restored only when it is a truncation of the identifier. The record link is written as metadata of the creation, so it needs `secret.create` (as the creation did), not `secret.rotate`, and the secret gets one Create audit entry. A disabled secret counts as holding its identifier: it is neither overwritten nor wrapped. Both migrate hidden and time-restricted records but not deleted ones; the deleted check follows TCA `ctrl.delete`, and a table without TCA is filtered on its `deleted` column. Tables mapped to another database connection are looked up there.
- `vault:migrate-field` refuses a `--uid-field` that does not exist or whose value several rows share, no longer wraps a value that is the identifier of an existing secret in a new secret (also with `--force`), fails a record whose identifier check against the vault errors and continues with the next one, and recognises a field named by a reserved word. The migration module no longer overwrites an existing secret whose identifier its pattern produces, and lists the reasons of failed rows on the verify page; a column with only row failures stays Partial.
- The orphan cleanup scheduler task logs through the LogManager when the scheduler builds it without dependency injection (TYPO3 13.4 unserializes tasks; 14.3 falls back to `makeInstance()` for a task that is not a public service). Before, such a task logged nothing.
